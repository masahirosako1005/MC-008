# 09. 店舗向けCMS 要件定義書（v0.1）

店舗と運営者（自治体・DMO）が、店舗情報・クーポン・イベント・店頭QRを登録し、来訪の集計を見るための管理画面（以下 CMS）の要件。
2026-11-09 作成。要件整理の段階で、実装はしない。数値はすべて（仮）。

- 現行の実装と設計は CLAUDE.md と docs/01〜08 に従う。本書には、それらの改訂が必要な内容を含む。
- 本書の内容を実装に入れるときは、先に §9 の該当文書を改訂する。
- 本番運用を前提に要件を整理する。そのうち発表デモで見せる最小版を、フェーズ1として切り出す（§8）。

## 0. 目的と位置づけ

### 0.1 目的

| 目的 | 企画書の根拠 |
|---|---|
| 店舗情報（営業時間・便利情報など）を新しく保つ | CLAUDE.md §10「店舗情報の鮮度：協力店から順に更新」 |
| クーポン・期間限定イベントを告知できる場にする。「期限」トリガーの元データにもなる | §3「期間限定イベント・クーポンの告知先を持てる」、§4.5 |
| 店頭QRで来店を証明し、なりすましを防ぐ | §4.2「店頭QRで訪問確定もできる（なりすまし対策・来店証明）」 |
| 地区別・曜日別の来訪傾向を、地域と店舗に返す | §3「地区別・曜日別の来訪傾向が見える（将来）」、§7.1「来訪データの活用」 |

### 0.2 原則（CLAUDE.md §5 をCMSに当てはめたもの）

1. **CMS は付加機能。** 店舗が参加しなくても、CMS が止まっていても、利用者アプリは成立する。
2. **機能ごとに貢献先を書く。** A（初回満足度）／B（未開拓への興味）／C（再訪動機）のどれに効くかを、すべての要件に書く。「－」は、それらを支える前提の機能（認証・監査など）を表す。
3. **失う体験を作らない（MUST-7）。** 次の CMS 操作をしても、利用者の成長Lv・カード・図鑑・ポイント・アイテムは減らさない。
   - クーポン・イベントの取り下げ
   - 協力店の解除
   - 閉店・非公開
4. **店舗には集計値だけを渡す（PRV-04）。** 個人を特定できる形では出さない。
5. **歩かずに稼げる仕組みは作らない。** 店頭QRでも位置情報を併用する。

### 0.3 範囲

| 対象 | 対象外（理由） |
|---|---|
| 店舗情報の編集、クーポン・イベントの登録、店頭QRの発行、来訪データの閲覧（集計） | 利用者アカウントの管理（端末IDだけで成立させる。D14） |
| 運営者の機能：アカウント承認、協力店の認定、掲載確認、名所の管理、カテゴリ辞書、監査ログ | 地区ポリゴン・地図背景・ライバルの編集（開発者が `scripts/master` で扱う） |
| 利用者アプリへの反映（公開データの配信） | 決済・課金、協力店の料金（未決 §10） |
| — | 個人単位の来訪データ（PRV-04） |
| — | 投稿の審査（フェーズ3。§2.6 の掲載確認の仕組みを流用する） |

## 1. 利用者とロール

### 1.1 ロール

| ロール | 想定する人 | 使う端末 |
|---|---|---|
| 店舗（オーナー） | 個人店の店主・店長。IT に不慣れなことを前提にする | 主にスマホ。PC でも使える |
| 運営者 | 自治体・DMO・商店街振興組合の担当者 | 主に PC |
| 開発者（CMS の外） | アプリの開発・保守を担う人 | — |

- フェーズ2では、店舗アカウント1つで1店舗を扱う。
- 複数店舗の兼務とスタッフ招待は、フェーズ3で入れる。

### 1.2 権限表

凡例：○＝できる、自＝自店だけできる、申＝申請して運営者の確認後に反映、×＝できない

| 操作 | 店舗 | 運営者 |
|---|---|---|
| 店舗情報（営業時間・臨時休業・便利情報）の編集 | 自 | ○ |
| 店舗情報（名前・カテゴリ・紹介文・写真）の編集 | 自・申 | ○ |
| 位置・地区・協力店フラグ・公開状態の変更 | × | ○ |
| 名所の情報の編集 | × | ○ |
| 自店のクーポン・イベントの登録（協力店だけ） | 自・申 | ○ |
| 名所のイベントの登録 | × | ○ |
| 掲載中のクーポン・イベントの取り下げ | 自 | ○ |
| 店頭QRの発行・再発行・失効（協力店だけ） | 自 | ○ |
| 来訪データの閲覧 | 自店の集計だけ | 全体の集計 |
| 店舗アカウントの承認・停止 | × | ○ |
| カテゴリ辞書の管理 | × | ○ |
| 掲載確認（承認・差し戻し・非公開化） | × | ○ |
| 監査ログの閲覧 | 自店の変更履歴だけ | ○ |

- 店舗IDは**サーバー側のセッションから決める**。リクエストに含まれる店舗IDは信用しない（SEC-01 と同じ考え方）。
- 画面で操作を出し分けるだけでは権限の確認とみなさない。必ずサーバー側で確かめる（SEC-03）。

## 2. 機能要件

**列の見方**
- 優先度：そのフェーズの中での優先度（Must／Should／Could。CLAUDE.md §8.2 と同じ意味）。
- フェーズ：§8 の段階。
- 基準：§0.2 の A／B／C／－。

### 2.5 来訪データ（集計値だけ。PRV-04）

| ID | 要件 | 優先度 | フェーズ | 基準 |
|---|---|---|---|---|
| CMS-D01 | **前提**：利用者アプリから、訪問記録をサーバーへ送る。利用者の同意（PRV-01）を得たうえで、送るのはスポットID・日時・地区だけ（D15、PRV-03）。生の座標は送らない | Must | 3 | － |
| CMS-D02 | 店舗が見られるもの：訪問数（日・週・月）、訪れた人の数、30日以内の再訪率（CLAUDE.md §9）、初めての人とリピーターの割合、曜日別・時間帯別の傾向 | Must | 3 | C |

| 項目 | 要件 | 関連 |
|---|---|---|
| 境界での検証 | CMS の入力・API・配信されたスナップショットは、利用者アプリと**同じ parse 関数と `TEXT_LIMITS`** で検証する（規則を1か所にまとめる） | DI-01 |

### 4.4 使いやすさ

- IT に不慣れな店員でも、スマホ1台で使えるようにする。PC とスマホの両方に対応し、幅は360pxから使える。
- 主要な操作は、ログイン後3タップ以内（仮）で始められるようにする。対象は「営業時間を直す」「臨時休業を入れる」「クーポンを登録する」「QR を出す」。
- タップ領域は44px以上。文字拡大（標準／大／特大）に対応する。
- 入力欄には、文字数カウンタと、どこが範囲外かの表示を付ける。保存する前に、利用者アプリでの見え方をプレビューできる。
- 状態（下書き・確認待ち・掲載中など）は、色だけに頼らず、文字とアイコンでも示す。

### 4.5 可用性・運用

- CMS は利用者アプリにとって必須の部品ではない。CMS や API が止まっても、利用者アプリは前回のスナップショットで動く。
- DB は日次でバックアップし、ステージング環境を用意する。
- 掲載ガイドラインと、運営者の確認の目安（例：2営業日以内）を決める。

### 6.3 クーポン・イベントの状態遷移

```
下書き ──申請──▶ 確認待ち ──承認──▶ 掲載予定 ──開始日──▶ 掲載中 ──終了日の翌日──▶ 終了
   ▲                │                 │                     │
   └───差し戻し──────┘                 └──────取り下げ────────┴──▶ 取り下げ
```

- 利用者アプリに配るのは、掲載予定・掲載中・終了の3つ。
  - 掲載予定は、スポット詳細に「予定」と出す（今の `CouponEventList` と同じ）。
  - 終了は、提灯アイテムを導出するために必要。
- 下書き・確認待ち・差し戻しは配らない。
- 取り下げたものは「期間を取り下げた日の前日までに短縮」して配る。開始日以前に取り下げたものは配らない。
  - 期間中に訪問した人の提灯アイテム（D16）を消さないため（CMS-E08）。
  - 実装：`domain/revisit/ShopEventDraft.ts` の `periodAfterWithdrawal`。

## 7. アーキテクチャの方針（詳しくは設計段階で決める）

### 7.1 本番（フェーズ2〜3）

- **CMS は別のエントリ・別のビルド・別のオリジン**にする（例：`admin.<ドメイン>`）。
  - 利用者アプリのビルドに CMS のコードと URL を含めない。

- **domain の共有**：`Spot`・`ShopEvent`・`Period`・ID・parse・`TEXT_LIMITS` は、利用者アプリ・CMS・サーバーで共有する（検証規則を1か所にまとめる）。

  - `SpotRepository` は「読み込んだら変えない」から「スナップショット単位で置き換える」に変える。
  - 置き換えは、画面の遷移時などの安全なタイミングで行う。
- 層の規則（01 §1）、JSDoc・ロガー（04）、static-audit（07）は CMS にも同じように適用する。

### 7.3 連携サーバー（連携の芯。2026-11-09）

PC の CMS とスマホのアプリのように、**別の端末どうし**でも登録内容が届くようにするサーバー。フェーズ2の「スナップショット配信（APP-01〜03）」の芯を先に作ったもの。ログイン・権限・掲載確認はまだ無い（フェーズ2の残り）。

**決めたこと（ユーザー決定）**
- 範囲は「連携の芯」：CMS の登録内容をサーバーに保存し、版番号付きの公開スナップショットとしてアプリへ配る。ログインは作らず、デモの「店を選ぶ」方式のまま。
- 技術（U1）：TypeScript＋Node 標準。`node:http` と `node:sqlite` だけで動き、依存パッケージを増やさない。サーバーは利用者アプリと同じ src（domain・application・検証の関数）を使う。

**仕組み**

```
CMS（PC）──HTTP──▶ 連携サーバー ──▶ SQLite（登録内容・変更履歴）
                     │ CMS のユースケースをサーバー側で実行（規則の確認＝SEC-03）
                     └─ 公開スナップショット（版番号・ETag）＋ SSE で版番号を通知
アプリ（スマホ）◀── 起動時に取得・SSE で変化を知ったら取り直す・前回の写しを localStorage に保存
```

- **規則はサーバーで確かめる**：協力店だけ・字数・期間・同時3件・二重登録の防止（操作ID）・楽観ロック（版数）は、フェーズ1と同じユースケースをサーバー側で動かして確かめる。CMS の画面は `HttpCmsServices`（`CmsServices` の HTTP 版）に差し替わるだけで、画面のコードは変えていない。
- **アプリはもう一度確かめる**：受け取った公開スナップショットは、マスタと同じ parse・`applyCmsOverlay` にかけてから重ねる（APP-05）。
- **止まっても動く**：サーバーにつながらないときは、前回の写し（`P+'cms.snapshot'`）で動く。写しも無ければマスタだけで動く（§4.5、APP-02）。
- **デモの日付**：CMS は DemoClock のずらし日数をヘッダー `x-demo-offset-days` で送り、サーバーはその日数の時計でユースケースを動かす（デモの版だけ）。
- **変更履歴**：保存のたびに「いつ・誰が・何を・前の値と後の値」を同じトランザクションで残す（DI-20。誰は今は `demo`）。
- **消しても版番号を戻さない**：デモのやり直しでも版番号は進める（配った版番号と食い違わないように）。DB のファイルを消して作り直すと版番号は 0 からになるので、「どの版か」は DB ごとの ID（`dbId`）と版番号の組で見分ける（ETag も `"cms-<dbId>-<版番号>"`）。やり直しは、ファイルを消すより CMS の「デモのやり直し」を使う。
- **二重登録を防ぐ**：CMS の画面は押すたびに新しい操作ID を作るので、サーバー経由では連打や時間切れ後の送り直しで二重に登録されうる。`WriteGuard` が、同じ内容の要求が送信中なら同じ結果を共有し、結果が分からなかった失敗のあとの送り直しは前と同じ操作ID で送る（DI-07。画面のコードは変えない）。
- **通知が止まってもつなぎ直す**：サーバーが 200 以外を返す（込み合い 503・中継の 502）と EventSource はあきらめるので、アプリ側で間を空けてつなぎ直す（3秒から、最長1分）。

**API**（道筋は `src/infrastructure/api/apiRoutes.ts` の1か所で決める）

| 道筋 | 用途 | 使える版 |
|---|---|---|
| `GET /api/health` | 動作確認（版番号・モード・SSE のつながり数） | 両方 |
| `GET /api/public/cms-snapshot` | 公開スナップショット（ETag。同じなら 304） | 両方 |
| `GET /api/public/cms-snapshot/stream` | 版番号の変化（SSE。つないだ直後に今の版番号を送る） | 両方 |
| `GET /api/cms/shops`、`GET /api/cms/shops/:spotId` | 店舗の一覧・店舗の情報 | デモだけ |
| `PUT /api/cms/shops/:spotId/info` | 営業時間・便利情報の保存 | デモだけ |
| `POST /api/cms/shops/:spotId/events`、`…/events/:id/withdraw` | クーポン・イベントの登録・取り下げ | デモだけ |
| `GET /api/cms/shops/:spotId/visit-stats` | 来店データ（ダミー） | デモだけ |
| `POST /api/cms/demo/reset` | 登録内容をすべて消す | デモだけ |

- API は、Host が `localhost` か IP アドレスの要求だけ受け付ける（403。DNS リバインディング対策＝攻撃者のドメイン名を 127.0.0.1 に向けても使えない）。
- 書込系は、`Content-Type: application/json` だけ受け付け（415）、Origin が自分のオリジンと違えば断り（403、SEC-28）、本文は 16KB まで（超えた時点で読むのをやめて 413）、1つの相手につき1分に120回まで（429、SEC-18）。
- SSE は全体で200本、1つの相手につき10本まで（503）。
- 失敗の応答は `{ ok:false, error:{ code, message, details } }`。details は文字・数値・真偽だけで、例外の中身は出さない。
- 公開スナップショットに入れないもの：処理済みの操作ID、開始日より前に取り下げたクーポン・イベント（§6.3）。
- **本番の版のサーバーは CMS の API を出さない**（ログインが無いため。MUST-8、SEC-02、SEC-03）。公開の API だけを出す。判定は `import.meta.env` を直接書いた式なので、本番ビルドでは CMS の API とユースケースが処理ごと消える（ビルドの大きさ 228KB → 170KB で確かめた）。

**https（2026-11-09）**

- スマホから開くときは `node scripts/dev/backend.mjs serve --host 0.0.0.0`。LAN に出すときは**自動で https になる**（平文のまま LAN に出さない）。自分の PC だけで https にするときは `--tls`。`dev` は自分の PC からだけ開ける（LAN に出すときは `serve` を使う）。
- 証明書は `scripts/dev/devCert.mjs` が Node 標準（`node:crypto`）だけで作る。依存パッケージ・openssl は要らない。
- **置き場所はリポジトリの外のユーザーごとのフォルダ**（Windows は `%LOCALAPPDATA%\machiquest\dev-tls`、それ以外は `~/.local/share/machiquest/dev-tls`。POSIX では 700/600）。共有 PC ではリポジトリのフォルダをほかの利用者も読み書きできることがあるので、認証局の鍵を置かない。起動時に場所を表示する。
  - `ca.crt`／`ca.key`：手元用の認証局（10年）。**名前の制限**（Name Constraints・重要）で、localhost と 127/8・10/8・172.16/12・192.168/16・::1、主体の名前は `O=MachiQuest Dev` の下だけに絞り、**用途もサーバー証明書（serverAuth）だけ**にする。OpenSSL と主要なブラウザ（Chrome・Safari・Firefox）はこの制限に従うが、従わない環境（Android のアプリ内の表示など）もありうるので、鍵は人に渡さず、**発表が終わったらスマホから認証局を消す**。
  - 使い回すときは、このスクリプトが作った形（名前の制限・用途あり、鍵と証明書が対）かを毎回確かめ、違えば作り直す（ほかの人が置き換えた制限なしの認証局を、知らずにスマホへ入れないため）。
  - `server.crt`／`server.key`：連携サーバーの証明書（EC P-256、1年＝ブラウザの上限 398日以内）。対象は localhost・127.0.0.1・::1・この PC の LAN の IPv4（社内の範囲のものだけ）。IP が変わったとき・期限が14日を切ったときは自動で作り直す。認証局は使い回すので、スマホに入れ直さなくてよい。
- スマホで警告を出さずに開くには、起動時に表示される `ca.crt` をスマホに入れて信頼する（入れなくても、警告を進めば開ける）。
- https で起動したときは、起動後に**認証局だけを信頼して https でつながるかを確かめ、つながらなければ止める**（平文のまま LAN に出さない）。サーバー側も、自分の PC 以外で待ち受けるのに TLS（か `--trust-proxy`）が無ければ起動しない。
- なぜ https か：アプリは `crypto.randomUUID` を使うため安全な文脈（https か localhost）が要り、LAN の http://192.168.… では起動しない。加えて、同じ Wi-Fi での盗み見・書き換えを防ぐ。
- 確かめたこと：
  - `scripts/dev/devCert.test.mjs`（8件）：OpenSSL の本物の TLS で認証局だけを信頼して検証に通る、名前の制限の外の名前（例 bank.example）の証明書は「permitted subtree violation」で落ちる、用途と名前の制限が付いている、置き換えられた認証局は使い回さない、使い回しと作り直しの条件。
  - `openssl verify -x509_strict -purpose sslserver` に通る。Windows の検証機構（schannel）でも、認証局だけを信頼して検証に通る。
  - 独立したレビュー担当に見てもらい、指摘（鍵の置き場所・使い回しの確認・認証局の用途・説明の言い過ぎ・平文で起動したときの止め方・引数の読み違い・IPv6 の中の IPv4・権限・通し確認の検証不足）をすべて直した。
- サーバーへは `--tls-cert`／`--tls-key`（PEM のパス）で渡す。サーバー側の https の受け口・TLS 必須・HSTS（名前の Host にだけ付ける）は、ログイン・認可と一緒に別の作業（jisui-share008-d4）で実装した。

### 7.4 ログイン・認可・本番向けの運用（2026-11-09。CMS-A04・A06・A07、§1.2、§4.1）

連携サーバーを本番として動かすための土台。ユーザー指示「本実装進めてほしい」。運用手順は `docs/11_backend_operations.md`。

**決めたこと**
- ログインは ID とパスワード（CMS-A04）。パスワードは Node 標準の scrypt（N=2^15・r=8・p=3。OWASP の推奨値）でハッシュ化し、`scrypt$N$r$p$salt$key` の形で保存する（SEC-19。Argon2id／bcrypt は依存パッケージが要るため、U1 の決定に合わせて scrypt）。
- セッションは HttpOnly・SameSite=Strict・Path=/api の Cookie `cms_session`。https（か TLS を終端する中継の後ろ）では Secure。DB にはトークンの SHA-256 だけを置く。期限はログインから 12 時間・最後の操作から 60 分（CMS-A06）。
- **同じ ID＋同じ相手（IP）**で失敗が 5 回続くと 15 分ロック（メモリで同期的に数えるので、並行して届いた失敗も数え漏れない。ほかの相手＝本人は締め出されない）。ログインの試みは 1 つの相手につき 1 分に 10 回まで。知らない ID・違うパスワード・ロック中のどれでも同じ計算をして同じ 401 と同じ文を返す（ID の有無・ロックの有無が分からないように）。
- ロールは店舗（shopOwner）と運営者（operator）。店舗の API は、道筋のスポットID をセッションの担当店舗と照らし合わせる（運営者はすべて。SEC-01）。店舗の一覧も担当する店舗だけを返す。運営者だけの操作（アカウント管理・デモのやり直し）は経路の `auth: 'operator'` で確かめる（SEC-03）。
- **本番の版でも店舗CMS の API を出す**（ログインが要る）。デモの日付・デモのログイン・デモのやり直しはデモの版だけ。
- **デモの「店を選ぶ」は本物のセッションで再現する**（CMS-A09 の置き換え）：デモの版の CMS は、セッションが無ければ `POST /api/auth/demo-login` で運営者として自動で入る。この API は**中継を通らず自分の PC から直接つないできたときだけ**受け付ける（ソケットの相手がループバック、かつ `--trust-proxy` でない、かつ中継を示すヘッダー（Forwarded・X-Forwarded-*・Via）が無く、Host が自分の PC を指す）。LAN に出しても、同じ Wi-Fi の人は運営者になれない。デモ用のアカウント（`demo.operator`・`demo.<スポットID>`）はパスワードでは入れず、本番の版ではそのセッションを通さない。
- CMS は利用者アプリと**別のオリジン**に置ける（§7.1）：`--cms-port` で同じプロセスが2つのポートで待ち受け、公開の面（アプリ＋公開 API）には店舗CMS・ログインの API を出さない。`--mode cms` のビルド（`dist-cms`）が店舗CMS だけの画面。
- 自分の PC 以外で待ち受けるときは TLS（`--tls-cert/--tls-key`）か `--trust-proxy` が無ければ起動しない（SEC-05）。HSTS は名前の Host にだけ付ける。`--allowed-hosts` で本番のホスト名を許可する（DNS リバインディング対策の延長）。読取系にも回数制限（1 分に 600 回）を付けた。`--trust-proxy` のとき、相手の IP は `X-Forwarded-For` の右端から `--proxy-hops`（既定 1）段さかのぼった値（左端は相手が書けるので使わない）。IPv6 は /64 で数える。Cookie の Secure は `X-Forwarded-Proto: http` と明示されたときだけ外す。
- 運営者は自分のパスワードを「作り直し」ではなく、今のパスワードを入れる変更でしか変えられない（席を離れた画面からの乗っ取りを防ぐ）。パスワード・トークン・Cookie の値はデバッグログにも出さない。
- 変更履歴の操作者（actor）はログイン中のアカウントID。ログイン・失敗・ロック・ログアウト・パスワード変更・アカウントの作成と変更は `cms_auth_log` に残す（SEC-24）。IP・パスワード・メールは残さない（SEC-25）。保持期間 3 年（仮）で古いものを 10 分ごとに消す（変更履歴も同じ）。
- 最初の運営者はコマンドライン `node dist-server/serverMain.mjs account create ...` で作る。以後は運営者が CMS の「アカウント」で作り、パスワードを作り直し、停止・再開する（CMS-A02・A07）。

**API**（道筋は `src/infrastructure/api/apiAuthRoutes.ts`）

| 道筋 | 用途 | 必要なもの | 使える版 |
|---|---|---|---|
| `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`、`POST /api/auth/password` | ログイン・ログアウト・ログイン中の人・自分のパスワード変更 | （login 以外）セッション | 両方 |
| `POST /api/auth/demo-login` | 運営者か店舗の担当者として入る | 自分の PC から | デモだけ |
| `GET/POST /api/cms/accounts`、`PUT …/:id/shops`、`PUT …/:id/status`、`POST …/:id/password` | アカウントの一覧・作成・担当店舗・停止と再開・パスワードの作り直し | 運営者 | 両方 |

失敗コードと HTTP：UNAUTHENTICATED・AUTH_FAILED＝401、FORBIDDEN・FORBIDDEN_SHOP＝403、ACCOUNT_NOT_FOUND＝404、LOGIN_ID_TAKEN＝409、ACCOUNT_LOCKED＝423、RATE_LIMITED＝429。

**画面**
- ログイン（C01。`screens/Login/`）：ID・パスワード・ボタンだけ。本番でセッションが無いときに出る。
- アカウント（C08。`screens/Account/`）：名前・ID・区分、パスワードの変更、ログアウト。上部バーのアカウントのメニューから。デモのアカウントでは変更とログアウトを出さない。

- 店舗のアカウントは、担当する店舗だけがお店の切り替えに出る（1店なら切り替え無し）。
